# P0.3b — tiled NVFP4 GEMM probe: a cubecl bug gates NVFP4 tensor-core (e4m3/factor-4)

**Probe:** `examples/nvfp4_gemm_probe.rs` (Codex). **Decisive result on GB10/sm_121:**

```
CANONICAL single-execute_scaled (NO two-call workaround), e2m1x2 × e2m1x2 → f32, e4m3 scales, scales_factor=4:
  positive scales: rows 0-7 max_abs_diff = 0.000000 (PASS)   rows 8-15 max_abs_diff = 55.01 (FAIL)
  signed scales:   rows 0-7 = 66.6 (FAIL)                    rows 8-15 = 62.8 (FAIL)
Tiled M=128 N=128 K=2048: max_abs_diff = 461.6 FAIL, 2.17 TFLOP/s
Shared memory: 2880 B used, fits 99 KiB = true  → the TRT-LLM smem/TMA trap is NOT the blocker at this tile size
```

## The finding (confirms Opus's P0.3 prediction)
The **canonical single-`execute_scaled` full-tile path is a cubecl codegen bug on the e4m3/scales_factor=4
route**: bit-correct for the **top half (rows 0-7)** with positive scales, **wrong for the bottom half (rows
8-15)**. The P0.3 single-tile probe only PASSed because its **two-call workaround** re-ran the MMA and read only
the (correct) top-half slots — masking the bug. The runtime test `kernel_scaled` only exercises
**ue8m0/scales_factor=2**, so the **e4m3/factor-4 bottom-half mapping was never tested** (Opus called this at
confidence 8/10; P0.3b confirms empirically). Likely locus: the accumulator register→row mapping
(`cubecl/.../cuda/processors.rs:107-111`) and/or the e4m3 scale-lane mapping for `scale_vec::4X`
(`cubecl/.../cuda/ptx/mma.rs`).

## Implication for the plan (DOWNGRADES the P0.3 GO)
- **NVFP4 tensor-core PREFILL + MTP-VERIFY are BLOCKED** by this cubecl bug — a real, fixable codegen bug, not a
  "pin bump." The P0.3 GO is scoped down to: *the instruction emits + runs + is correct for the top half /
  ue8m0-factor-2; the e4m3/factor-4 full tile is broken.*
- **NVFP4 DECODE is SIMT (no tensor cores) → UNAFFECTED.** The main single-stream lever (decode weight-bytes)
  proceeds on the SIMT dequant-in-load GEMV regardless of this bug.
- Good news: the **99 KiB smem trap is NOT hit** at this tile (2880 B) — so once the correctness bug is fixed,
  the shared-mem ceiling is not the immediate blocker (the probe used synchronous barriers, not an async
  double-buffered K-loop, so 2.17 TFLOP/s is un-tuned, not a ceiling).

## Path forward (options; final pick from the 3-voice review → see GSTACK section / plan §2a)
- (a) **Fix the cubecl codegen** locally (`/workspace/cubecl` is our patched copy) — aligns with "improve
  burn/cubecl"; unblocks real NVFP4 tensor-core. Risk: deep codegen debugging.
- (b) **ue8m0/scales_factor=2 (MXFP4)** instead of e4m3 NVFP4 — different format (shared-exponent block scale);
  accuracy/checkpoint implications (NVFP4 checkpoints ship e4m3 block scales).
- (c) **2-call workaround** — ~2× tensor-core work / ~half throughput; only worth it if (a) is too costly.
- (d) **Defer NVFP4 tensor-core**: keep NVFP4 decode-SIMT only, prefill stays bf16, MTP-verify not on TC.
  Defensible because prefill is one-time TTFT and MTP is last + ~1.2× diluted on this top-8 MoE.

**Net: this does NOT block the critical path (NVFP4 decode-SIMT). It blocks the secondary compute-bound NVFP4
shapes (prefill/verify) until a cubecl fix (P0.3c) or a format/workaround choice.**

## 3-voice synthesis + OPERATING DECISION (Codex + Gemini + Opus 4.8, unanimous)

**Confirmed cubecl bug, NO-GO on canonical NVFP4 tensor-core today.** Root cause (Opus 8.5/10, Codex 0.7,
Gemini 0.9): the **`scale_vec::4X` scale-factor row→(thread,selector) mapping** — `frontend/cmma.rs:502`
(`scales_index = quad_id + (t_id%2)*8`, tuned for the 2X layout) + `ptx/mma.rs:173-176` (tidA/bidA/tidB/bidB
hardcoded to 0). Validated only for ue8m0/scale_vec::2X; **e4m3 + 4X (real NVFP4) has zero cubecl test
coverage** → shipped broken. Ruled out: accumulator mapping (rows 0-7 exact) + factor-4 indexing (top rows
exact across all 4 K-blocks). Signed-scale failure is a separate expected effect (E4M3→ue4m3, sign ignored).

**OPERATING DECISION = (d) now + (a) in parallel:**
- **(d) Defer NVFP4 tensor-core NOW (operating assumption for Lane work):** prefill stays **bf16** (one-time
  TTFT; the tiled NVFP4 probe hit only **2.17 TFLOP/s = no win over bf16 anyway**), **NVFP4 decode runs SIMT**
  (unaffected — carries the real single-stream win), **MTP-verify off tensor-core** (last layer, ~1.2× diluted
  on the top-8 MoE). Zero correctness risk; unblocks all downstream work immediately. **Lane 1/2/MTP proceed on
  this basis.**
- **(a) Fix cubecl in parallel = P0.3c (running):** patch `scales_index` bottom-half + plumb real tidA/bidA
  selectors through `ptx/mma.rs`; add the missing e4m3/factor-4 all-16-rows regression test. A genuine
  upstreamable cubecl improvement. **Medium effort/risk (Opus 6/10 — a PTX-ISA reverse-engineering job, not a
  one-liner)**; P0.3c has a clean fallback: if too deep, revert the patch, keep the failing test, stay on (d).

**Bottom line: this bug does NOT gate the plan.** Decode-SIMT (critical path) is unaffected; prefill/MTP-verify
ride bf16 until P0.3c lands NVFP4-TC as a bonus.

## P0.3c CLOSURE (correction — it was an additive fix, NOT a regression)

Codex fixed the real root cause (NOT the 3-voice scale-lane hypothesis): `compile_scaled_mma` emitted scalar
`frag_d[0..3]` accumulator registers, but for vectorized `Array<Line<f32>>` that produced OOB `float_2` accesses
(`l_arr[2/3]`) → bottom-half garbage. Patch = scalar/vector-aware accumulator formatting in
`cubecl-cpp/.../ptx_wmma_compiler.rs` + a new `test_cmma_scaled_fp4_e4m3_factor_4` runtime test.

**Mid-course correction (verified by experiment):** I initially flagged a regression because
`test_cmma_scaled` + `test_cmma_scaled_fp4` failed after the patch. A `git stash` of my changes proved those
two tests **FAIL at pristine cubecl HEAD (2cafb762) too** — they are **pre-broken in this local cubecl fork,
independent of P0.3c**. So P0.3c is a clean **additive** fix: it makes the canonical e4m3/factor-4 single-MMA
correct (rows 0-15) without touching the (separately, pre-existing) broken ue8m0/fp8 test paths.

**Final P0.3c state (verified):** `test_cmma_scaled_fp4_e4m3_factor_4` PASS (un-ignored);
`nvfp4_gemm_probe` canonical positive-scale rows 0-15 `max_abs_diff=0.0 PASS`; engine builds. Kept as a genuine
upstreamable cubecl improvement + the regression test that was missing. **Out of scope (pre-existing, flagged):**
`test_cmma_scaled`/`test_cmma_scaled_fp4` are red at this fork's HEAD — a separate ue8m0/fp8 scaled-MMA issue to
report upstream, unrelated to NVFP4. Operating decision unchanged: **(d) defer NVFP4-TC** (tiled GEMM still
fails + 2.16 TFLOP/s = no bf16 win); the canonical-instruction fix is banked for when NVFP4-TC is adopted.
