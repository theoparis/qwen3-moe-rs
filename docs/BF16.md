# bf16 mixed-precision training

This document explains the bf16 path: the recipe, why it's correct, how it's wired, what's verified,
and the known limitations.

## The recipe

bf16 (`bfloat16`) has the same 8-bit exponent as f32 (so the same dynamic range — no loss scaling
needed) but only a 7-bit mantissa. That mantissa is fine for matmul *inputs* but fatal for
*accumulation*: a small optimizer step added to a larger weight rounds to zero, and training silently
stalls. The standard fix (PyTorch AMP, Candle, etc.) is **mixed precision**:

- **f32**: master weights, optimizer state, RMSNorm, softmax, residual adds, the final logits/loss.
- **bf16**: only the compute-heavy Linear GEMMs (q/k/v/o, gate/up/down), with **f32 accumulation**.

So you get the bf16 tensor-core throughput on the matmuls without the mantissa-rounding failure on the
weight updates.

## How it's wired

`linear3(lin, x, prec)` is the single seam (`src/linear2d.rs`). With `Precision::Bf16`:

```rust
// cast inputs to bf16, matmul (CUDA accumulates in f32), widen the bf16 output back to f32:
a.cast(DType::BF16).matmul(w.cast(DType::BF16)).cast(DType::F32)
```

- **f32 accumulation is the kernel's job.** On the CubeCL CUDA backend the matmul of bf16 inputs
  accumulates in f32 registers (`cubek` `MatmulPrecision for bf16 { Acc = (bf16, f32) }`) and writes
  a bf16 output, which the trailing `.cast(F32)` widens. The accumulation is f32; the activation
  carries bf16 rounding — exactly like a PyTorch bf16-autocast Linear.
- **The gradient lands in f32.** Burn's `float_cast` is differentiable and its backward returns the
  gradient in the *source* dtype, so the per-forward `weight.cast(BF16)` routes an f32-typed gradient
  back to the f32 master weight. The optimizer (AdamW) therefore keeps f32 state.
- **Decoupled train/infer precision.** `Qwen3ForCausalLM` carries `train_precision` (used by
  `forward`) and `infer_precision` (used by `forward_with_cache` / `generate`, default `F32`). Set
  training precision via `with_train_precision(Precision::Bf16)`; inference stays f32, so bf16 training
  never changes generation or Hugging Face logit parity.

## Verified (NVIDIA GB10, sm_121)

All numbers below were measured on the CUDA backend at the pinned Burn rev. The **matmul-parity**
and **throughput** rows reproduce from the public examples (see "Reproduce" below). The
**convergence**, **gradient-parity** and **freeze-head-ablation** rows were measured with a training
harness that depends on a private dataset and is not part of this public repo — they are reported
here as evidence, not as a public repro.

| Check | Result |
|-------|--------|
| bf16 2-D matmul vs f32 (parity) | cosine **0.999996**, relative Frobenius error **0.0029** |
| Batch-safety (`linear3`, identical rows) | `\|row0 − row1\| = 0` at all tested shapes (3-D broadcast path diverges) |
| bf16 forward-logit parity (full model) | cosine **0.999980** vs f32 |
| Gradient-norm parity (tied embedding) | bf16 vs f32 relative diff **0.0010** |
| bf16 single-batch overfit convergence | loss **3.20 → 0.0588** (f32: 3.20 → 0.0703); tracks the f32 floor |
| Freeze-head ablation (only bf16 Linears train) | loss **3.20 → 0.0891** with the embedding+head frozen — proves the bf16 gradient path actually trains, not the f32 head memorizing |
| Throughput (Qwen3-0.6B, batch 8–16 / seq 512) | bf16 **1.06–1.09×** f32 (device-synced) |

The freeze-head ablation is the load-bearing correctness test: a single-batch overfit can pass on the
f32 tied head alone even if the bf16 gradients are broken, so we freeze the head and require the bf16
Linears to drive the loss down on their own.

### On throughput

bf16 is only ~1.06–1.09× on Qwen3-0.6B: at this size the per-forward weight cast plus the still-f32
attention and LM head bound the step, so the bf16 GEMM win is modest. The advantage is expected to grow with
model size as the Linear GEMMs come to dominate the step (not measured here — only 0.6B was tested). `bench_bf16` reproduces this (it syncs the device before stopping
the timer — CubeCL is async, so an unsynced wall-clock would over-report).

## Reproduce

```bash
# bf16 matmul parity + batch-safety, and the 3-D broadcast bug it avoids:
RUSTFLAGS="-C target-feature=+fp16" cargo run --release --features cuda --example matmul_probe

# bf16-vs-f32 throughput (configurable: BATCH, SEQ, STEPS):
RUSTFLAGS="-C target-feature=+fp16" BATCH=8 SEQ=512 STEPS=8 \
  cargo run --release --features cuda,train --example bench_bf16
```

## Limitations

- **bf16 inference is unsupported.** `forward_with_cache` panics with a `DTypeMismatch` in `RmsNorm`
  on the Fusion backend (a bf16-matmul → cast → norm dtype-tracking issue). `with_infer_precision`
  rejects `Bf16`; inference runs in f32. bf16 is for training.
- **CUDA-validated only.** `Precision::Bf16` is verified on the CubeCL CUDA backend, whose matmul
  accumulates in f32. Other backends may not support a bf16 matmul or may accumulate in bf16 — using
  `Bf16` there can panic or silently change numerics. `F32` (default) is safe on every backend.
- **Precision is runtime config, not serialized.** It's stored in `Ignored<_>` fields, so it does not
  travel with a model record. A freshly built or checkpoint-loaded model defaults to f32 — re-apply
  `with_train_precision` after loading. Before scaling to multi-GPU (where Burn copies the model to
  workers via records), make precision serializable (move it into `Qwen3Config`); otherwise the master
  could train bf16 while workers silently fall back to f32.
