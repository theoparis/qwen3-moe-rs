# P0.3b spec — tiled multi-warp NVFP4 GEMM probe (the real de-risk)

Derived from the unanimous 3-voice P0.3 review (`docs/P0.3-scaled-mma-findings.md`). P0.3 proved the NVFP4
scaled-MMA *instruction* works on sm_121; P0.3b proves (or refutes) a *usable, performant tiled GEMM* — the
thing that actually gates NVFP4 prefill + MTP-verify. **This is the single decisive Phase-0 probe for the quant
lever.**

## Deliverable
`examples/nvfp4_gemm_probe.rs` — a fixed-shape tiled NVFP4 GEMM at a representative prefill shape (one expert's
W1/W3: M≈256 tokens × N=`moe_intermediate_size` × K=`hidden`), on raw `CudaRuntime` (not Fusion).

## MUST do (each item resolves a specific review finding)
1. **Natural 4-register accumulator, ONE `execute_scaled` per K-step — NO two-call "8-row half" workaround**
   (Opus's #1 finding). This directly tests whether the canonical single-MMA full-tile path is correct on the
   **e4m3 / scales_factor=4** route (the fp4 runtime test only covers ue8m0/factor-2, so e4m3 bottom-half may be
   untested). If rows 8-15 come out wrong → **file a cubecl bug, downgrade the P0.3 GO**; the workaround would
   otherwise double tensor-core work.
2. **Shared-memory staging + double-buffer** for A, B, and the per-block scales; **print actual smem bytes used
   vs the 99 KiB/block cap** and the achieved **occupancy (warps/SM)**. This is the TRT-LLM trap — measure it
   explicitly (their NVFP4 CUTLASS path collapsed to ~4.8 tok/s on SM121 here).
3. **K-loop accumulation** over the full K (register-resident f32 accumulator across many m16n8k64 MMAs).
4. **Multi-warp, multi-tile**: multiple warps/CTA, multiple CTA output tiles (M=64–256, N=64–128).
5. **Throughput vs TWO baselines**: report TFLOP/s (or prefill tok/s) against (a) the **bf16 tensor-core** path
   and (b) the existing **SIMT** path. **A GO requires beating bf16.** If it loses to bf16, NVFP4 prefill is
   not worth it on GB10 → fall back (FP8) and keep decode SIMT.
6. **Realistic numerics** (Opus #3): values that genuinely round in E2M1; **≥1 negative block scale** (exercise
   the `ue4m3` sign-ignore the probe never tested); the **per-tensor FP32 second-level scale** real NVFP4
   checkpoints use; **large K** (accumulation/reduction-order stress, not the clean K=64). Compare vs an f32
   reference.

## The single decisive number
**Sustained TFLOP/s at an occupancy that fits 99 KiB shared memory, relative to bf16.** Everything else is
correctness gating.

## Risk to watch (Gemini)
CubeCL's arch-120-130 backend may lack `wgmma`-style async K-loop → synchronous pipeline stalls. If the K-loop
can't overlap MMA with the next tile's smem load, throughput may stay compute/latency-bound regardless.
